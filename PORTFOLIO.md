# Prove the model before you trust the camera.

**→ Model Validator · 2026** · `AC`

![Prove the model before you trust the camera. thumbnail](/thumbnails/accel-thumb.png)

Accel takes a computer vision model from “trained” to “trusted” — build the model and its rules, validate against real footage, deploy only what passes, then monitor it running live. A full-stack, on-premise Vision AI operations platform I designed end-to-end.

**Metrics:** Vision AI Ops · Sigmawave AI · May–Jul 2026

**Live:** https://delbintoehtet-portfolio.vercel.app/work/accel

*Designing Accel — a Vision AI operations platform for defence and security operators.*

Accel is where a computer vision model goes from “trained” to “trusted.” Operators build a model and the rules it runs on, validate it against real footage, deploy only what passes to cameras across their sites, then monitor it running live — all in one on-premise platform they fully own. I designed the whole thing: model and rule creation, the validation pipeline, the deployment layer, the live monitoring wall, and the admin spine that governs it. The promise built into every screen: complete operator autonomy from day one.

**AT A GLANCE · 60 SECONDS**

### A model that scores well can still fail on a real camera.

A computer vision model can pass every benchmark and still miss a person in bad light, misread an unfamiliar angle, or flag a shadow as a threat. In real deployment those failures surface late — on a live camera, when remediation is expensive. Accel closes that gap. Operators build a model and its rules, validate it against real footage, deploy only validated models to cameras, and monitor them at work — without stitching together five different tools to do it. My job was to design every surface in that loop and make a genuinely complex operations platform feel like one coherent path.

`Model Creation` · `Rules Library` · `Run Analysis` · `VLM Reasoning` · `Deployment` · `Live Monitoring` · `On-Premise`

- **Problem:** Models get deployed on trust, not proof. Validation is fragmented across tools, and defining detection logic usually needs an engineer.
- **Method:** Designed around one operator loop — build, validate, deploy, monitor — organised into five clear platform sections, against a three-role permission matrix.
- **Decision:** Make Run Analysis the differentiator: a model must be validated against real footage, with VLM reasoning, before it can be deployed.
- **Surfaces:** Model management, rules, run analysis, deployment, dashboard, live monitoring, recordings, incident reports, sites, cameras, NVRs, users, billing.
- **Outcome:** A platform that takes a model from “built” to “validated” to “deployed and watched” — fully on-premise, fully operator-owned.
- **Lesson:** In a complex operations tool, the hardest and most valuable design work is making the right path the obvious one.

**THE PROBLEM**

### 01 · Models get deployed on trust, not proof.

*And trust is the wrong currency for a detection model.*

Computer vision teams working with synthetic and hybrid-synthetic data face the same three problems again and again. There's a validation gap — models that score well in testing fail in real conditions because of lighting, angle, occlusion, and environmental variation, and those failures only surface after deployment when they're expensive to fix. There's tooling fragmentation — teams stitch together separate platforms for dataset management, video testing, performance visualisation, rule definition, deployment, and monitoring, and the seams between them hide root cause and slow every iteration. And there's detection-logic accessibility — defining when a model should trigger an alert usually requires an engineer, locking out the operations and domain experts who understand the use case best.

Accel had to close all three at once, for operators in defence and security who need to run, manage, and own their Vision AI on their own infrastructure. My job was to design that unified loop — and make it something operators actually run, not something they skip under pressure.

- **Validation gap** — Models that score well in testing fail in real conditions because of lighting, angle, occlusion, and environmental variation — and the failures only surface after deployment, when they're expensive to fix.
- **Tooling fragmentation** — Separate platforms for datasets, video testing, performance visualisation, rule definition, deployment, and monitoring. The seams between them hide root cause and slow every iteration.
- **Detection-logic accessibility** — Defining when a model should trigger an alert usually requires an engineer — locking out the operations and domain experts who understand the use case best.

> A model you haven't validated isn't a capability. It's an unproven assumption sitting on a live camera.

![The gap — model trained vs model proven on real footage](/casestudies/accel-1.png)

**THE FRAME**

### 02 · One operator loop. Five sections.

*Build → validate → deploy → monitor, plus the governance around it.*

Rather than design seventeen modules as seventeen problems, I designed one loop and organised everything into five top-level sections that follow it. Operators Manage their sites, cameras, NVRs, models, and rules — building the detection logic first. They Deploy — but only after Run Analysis validates a model against footage. They Monitor the live result on a dashboard, camera wall, and incident feed. And the System and Profile sections hold the governance — users, device health, configuration, activity logs, and billing — that keeps the loop safe and accountable.

That framing settled the priorities early. It's why a model is built and its rules attached before anything else. It's why validation comes before deployment, not beside it. And it's why live monitoring is framed as the payoff of the loop, not a separate product bolted on.

> I stopped counting screens and started counting steps in one operator loop. The sections organised themselves after that.

![Section map — Monitor / Manage / Deploy / System / Profile](/casestudies/accel-2.mov)

**MANAGE MODELS**

### 03 · Build the model. Write the rules.

*The detection logic comes first — and a non-engineer can define it.*

Before a model can be proven or deployed, it has to be built. Model Management is where a detection model is assembled as an SOP-compliant sequence of processing steps — uploaded as JSON or .onnx files, each with an action or model label — with rules attached from the library or added inline. The result is a single model artefact: an ordered sequence of steps plus the rules that govern it, ready for validation.

The Rules Library is the detection-logic layer, and it's the answer to the “you need an engineer” problem. Operators compose rules from structured conditions, start from pre-built templates (perimeter intrusion, PPE compliance, crowd density), and every rule carries an auto-generated plain-English summary so a non-engineer can read exactly what it does before saving. Rules assign the severity that ranks detections downstream, and they attach directly to models — so the logic and the model that runs it are never separated.

![Model Management — SOP sequence builder with attached rules](/casestudies/accel-3.mov)

![Rules Library — template-based builder with plain-English summary](/casestudies/accel-4.mov)

> Rules written in plain English are how a domain expert — not just an engineer — gets to define what the system watches for.

**RUN ANALYSIS**

### 04 · The MVP differentiator.

*Upload footage, run the model, read the verdict — with reasoning.*

Run Analysis is where a built model gets proven, so it earned the most design attention. The flow is deliberately linear: select a model, select a preferred SOP VLM to reason about the footage, upload a representative video clip, and run. What comes back isn't just a number — it's a score, an activity log, and a VLM reasoning narrative that describes and explains what the model saw and why it behaved the way it did. The whole run is exportable as a report.

That reasoning narrative is what makes the verdict trustworthy instead of opaque. A score alone tells an operator whether a model passed; the VLM narrative tells them why — which is what lets a domain expert, not just an ML engineer, decide if the model meets the bar. Past analyses are kept and searchable, so a model's track record — every run, score, and report — is never a mystery.

![Run Analysis — select model, select SOP VLM, upload footage](/casestudies/accel-5.mov)

![Analysis result — score, activity log, VLM reasoning narrative, export](/casestudies/accel-6.mov)

> The whole platform rests on one moment: a verdict an operator can trust. The VLM reasoning is what turns a score into a decision.

**DEPLOY MODELS**

### 05 · Put the proven model on a camera.

*The hinge between validation and live production.*

Deployment is where a validated model meets real hardware. An operator maps a proven model to a specific site, area, and camera through search and filter, and it begins continuous frame-by-frame rule evaluation on the live stream. Only a model that has passed Run Analysis reaches this point — validation is what earns a model its place on a camera.

Designing this meant making “what's running where” legible at a glance. Deployment history keeps the full operational context — which model watches which camera, across which sites, deployed by whom, against which last validation reference — with direct navigation from the deployment view straight into any linked camera to edit settings or review recordings. An operator always knows exactly which proven models are live, and where.

![Deploy Models — mapping a validated model to site / area / camera](/casestudies/accel-7.mov)

![Deployment history — what's running where, with validation trail](/casestudies/accel-8.mov)

> Validation earns the right to deploy. Deployment is where that proof becomes something running on a live feed.

**MONITOR**

### 06 · Watching validated models at work.

*The payoff for the whole loop — readable under pressure.*

Once models are deployed, the Monitor section is where their work shows up. The Dashboard is the central operations screen: real-time panels for detection performance and operational events, a persistent time filter (today, 7 days, 30 days, custom) applied across every panel, and drill-down into the modules beneath. Live Monitoring is the multi-camera grid with configurable layouts and per-tile feed-health indicators, plus active/inactive camera counts. Recordings lets operators search past footage by site, area, camera, date, or keyword and play it back against a synchronised, severity-filterable event timeline.

The Detection Feed is the raw stream of what models are catching — filterable by time, site, area, severity, camera, or model, with counters for total detections, critical/high, pending triage, and escalated cases. Each detection carries its model, severity, precision and confidence scores, and location — with a clear call to action: raise it as an official Incident Report, dismiss it, or attach it to an existing report. Incident Reports are the accountable layer: auto-generated from high-severity events or created manually, moving through a Pending → Acknowledged → Resolved lifecycle, each one audit-ready, linked to exact footage timestamps, and exportable as a PDF.

![Dashboard — real-time panels with persistent time filter](/casestudies/accel-9.mov)

![Live Monitoring — multi-camera grid with feed-health indicators](/casestudies/accel-10.mov)

![Detection Feed → Incident Report handoff, model + score trail](/casestudies/accel-11.mov)

> A detection is only useful if it becomes accountable work. The path from “the model flagged this” to “someone owns this” had to be a couple of clicks.

**THE ADMIN SPINE**

### 07 · Who can do what, and whether the hardware is healthy.

*Governance one layer back from the hot path.*

Around the operator loop sits the System section, designed against a three-role matrix — Owner, Admin, User — so what each person can see and do is a deliberate decision, not an accident of routing. User Management handles email-invite onboarding, role assignment, and lifecycle actions.

![User Management — three-role matrix, invite and lifecycle actions](/casestudies/accel-12.mov)

### What this project taught me.

- **Design the loop, not the module count.** Seventeen modules sounds like seventeen design problems. It was really one operator loop — build, validate, deploy, monitor — repeated at different altitudes. Framing it that way kept a dense platform coherent instead of sprawling.
- **Make the right path the only path.** Validation only protects an operator if it comes before deployment by design. Making Run Analysis the gate, not a suggestion, did more for the product's promise than any amount of persuasive UI.
- **A score needs a reason.** The most trustworthy thing in the validation flow is the VLM reasoning narrative. A number tells you whether a model passed; the reasoning tells you why — and that's what lets a domain expert make the call instead of an engineer.

**TIME MACHINE**

### If I could go back.

I'd get the Run Analysis flow in front of real operators sooner. I designed the validation loop — footage in, score and VLM reasoning out, exportable report — mostly through my own reasoning and internal review. It holds up, but one session watching an operator validate a model they actually cared about would have surfaced friction faster than another round of my own iteration.

And I'd pin down the three-role permission matrix before designing the surfaces, not alongside them. Role rules ended up shaping nearly every screen; settling who can do what up front would have saved rework each time a “should a User see this?” question reopened a layout I'd already called done.

Terra generates synthetic data to train AI vision models — the datasets that are dangerous, expensive, or impossible to collect in the real world. A working version already existed. My job was to redesign it: better usability, more features, and a real fix for the pain points users hit in the original. I owned it end-to-end, from competitor research to the final 3D builder.

**AT A GLANCE · 60 SECONDS**

### The tool worked. It just needed to be better.

Terra wasn't new. A working version already shipped — but it was rigid. Scenes were hard to customise, there was no real camera control, lighting was fixed, and teams couldn't scale their work. I redesigned the whole thing: benchmarked the leading synthetic data tools, learned Blender and Unreal so I actually understood the 3D work our users did, gathered feedback from real users of the old version, and rebuilt Terra around a focused, canvas-first 3D builder.

`Redesign` · `3D Builder` · `Scene Control` · `AI Features` · `Dataset Generation` · `Design System`

- **Problem:** The original Terra worked, but it was rigid: limited scene customisation, no camera control, fixed lighting, poor scalability for teams.
- **Method:** Benchmarked competitors, took a month of Blender and Unreal training, gathered feedback from existing users, then rebuilt the flow.
- **Decision:** Redesign around a canvas-first 3D builder where users interact with scenes in real time — not a rigid, disconnected editor.
- **Surfaces:** Dashboard, org management, 3D scene editor, object and environment settings, timeline, generation and export.
- **Outcome:** A platform that turns scene-building into real, train-ready datasets — auto-annotated and ready to drop straight into a model pipeline.
- **Lesson:** The best design comes from staying close to the real work users are trying to do.

**THE PROBLEM**

### 01 · It worked. It was just rigid.

*A working product that users couldn't move freely inside.*

Terra already had a working version when I joined the project. The technology was sound — it generated synthetic data. But using it was the problem. Scene customisation was limited. There was no way to move the camera, no precise object placement, no way to preview how a scene would look under different lighting. Editing felt disconnected, and the platform didn't scale for teams.

My role as Product Owner and Designer was to redesign it — better usability, more features, and a real fix for the pain points users faced in the original.

> The product wasn't broken. The experience was. My job was to redesign the experience without breaking what worked.

![Terra old version — the original interface](/casestudies/terra-1.png)

**EXPLORE**

### 02 · I didn't design first. I learned first.

*Benchmarks, then a month inside Blender and Unreal.*

To know what to design, I studied the field. I benchmarked the leading synthetic data platforms — Synthesis AI, Anyverse, Bifrost AI, Parallel Domain — to understand where the industry bar sat and where Terra could go further.

But Terra runs on 3D workflows, and I couldn't design for something I didn't understand. So I took a month of Blender and Unreal Engine training with top creators — scene design, materials, lighting, animation. That month changed how I designed. I stopped guessing at what a 3D artist needed and started designing from how the work actually gets done.

> You can't design a 3D tool from the outside. I learned the craft first, then designed for it.

![Benchmark board — competitor tools compared](/casestudies/terra-2.png)

**DEFINE**

### 03 · What the new Terra had to solve.

*Straight from the people who used the old one.*

I reached out to users of the previous version and gathered direct feedback. The same problems kept surfacing: limited scene customisation, unintuitive tools, minimal control over rendering, and poor scalability for teams.

I spent the following weeks turning that into direction — pulling best practices from the platforms and creative tools I'd studied, and building a new user flow that reflected the expanded feature set and fixed the old limitations. This phase wasn't just about refining the experience. It was about expanding what the product could be.

![New user flow — the redesigned journey](/casestudies/terra-3.png)

### 04 · Getting everyone to see it before building it.

*Mid-fidelity proposal, early feedback, aligned direction.*

Before touching high-fidelity design, I brought the research and early concepts to stakeholders. I walked them through the proposed user flows, showed how each feature answered a specific pain point from the old platform, and laid out the key improvements planned for the new version.

To make the direction tangible, I prepared a mid-fidelity proposal showing how the updated layout would look and work. It let stakeholders see the redesign clearly and give feedback early — before it was expensive to change.

![Mid-fidelity proposal shown to stakeholders](/casestudies/terra-4.png)

**DESIGN**

### 05 · Same product. A frame that finally fits.

*The redesign, told through the moments that define it.*

With research, layout direction, and the revised flow aligned, I moved into high-fidelity design. Here are the moments that define how the new Terra works.

**THE DASHBOARD**

### Users used to lose track of their own work.

The old dashboard had no visual hierarchy and made resuming or managing multiple projects a chore. I rebuilt it around a visually rich project overview — recently opened projects shown as large, recognisable thumbnails with key metadata like last edit date and owner, so users can pick up where they left off and collaborate fast.

Navigation was the other pain point. Jumping between projects or finding admin tools felt clunky, so I restructured the sidebar and tab system for seamless workspace switching. Tools like project settings and org management sit contextually — there when you need them, out of the way when you don't.

![Terra redesigned dashboard — project thumbnails, restructured sidebar](/casestudies/terra-5.mov)

**THE BUILDER**

The old Builder was missing the basics users expected. Editing felt rigid and disconnected — hard to build anything dynamic or realistic. I reimagined the whole thing around a focused, canvas-based interface where users interact with their scenes in real time. Two panels carry most of the weight: Object Settings and Environment Settings.

**THE AI LAYER**

### Two features define where the product is heading.

The redesign also brought in AI features I designed end-to-end. A third, Auto Segment Anything (ASA), handles automatic image segmentation and occlusion between real images and 3D objects — designed, but not covered in depth here.

### Two AI features, designed end-to-end.

- **Restyle (MAT)** — Synthetic data often looks synthetic. MAT lets users upload a real-world reference image, and Terra extracts its visual characteristics — lighting, colour grading, noise, lens artifacts — and applies them to the synthetic output. Users control the strength and preview before exporting. The goal: datasets close enough to real that models actually generalise.
- **Sigma Agentic Builder (SAB)** — AI-assisted scene building. Instead of placing every object by hand, users describe what they want and the system helps assemble it.

**GENERATE & DATASETS**

### 06 · From scene to train-ready data.

*The whole point of Terra: usable ML data, not just pretty renders.*

The generation flow ties it together. A user builds a scene, hits Generate, picks image or video, and the system processes the job in the background. A Work Orders panel tracks every job — in progress, completed, failed — so users can queue multiple generations and come back when they're ready.

What comes out is the payoff: datasets auto-annotated in COCO, YOLO, or Pascal VOC — labeled, structured, and ready to train on with no manual annotation step. That's the difference between a 3D render and a training asset.

**THE PROOF**

### I took the dataset straight into Roboflow.

To prove the loop closes, I took a batch of Terra-generated images straight into Roboflow and trained a model on them — no real-world photos in the set. The dataset dropped in cleanly, annotations intact, and trained without manual cleanup. That's the whole thesis of the product in one test: build a scene, generate, train.

![Roboflow — Terra dataset uploaded, training run on generated images](/casestudies/terra-13.png)

> A synthetic data platform is only as good as what a model can learn from it. The dataset going straight into Roboflow and training clean was the real proof.

### What this project taught me.

- **Learn the craft before you design for it.** A month in Blender and Unreal changed every decision that followed. You can't design a 3D tool well from the outside — I had to understand how scenes are actually built, lit, and rendered first.
- **The best direction comes from the old product's users.** The people who struggled with the original version told me exactly what to fix. Listening to the real work beat any assumption I could have made in Figma.
- **The dataset is the deliverable, not the scene.** It's easy to over-invest in how the editor looks and forget users come for train-ready data. Designing generation and export to end in clean, labeled output mattered as much as any editor panel.
- **Ownership means deciding what matters.** As Product Owner I defined the MVP, prioritised features, and shaped the vision from the ground up. That freedom only works if you stay disciplined about what actually earns its place.

**TIME MACHINE**

### If I could go back.

I'd get real users into the redesigned Builder sooner. The research and stakeholder alignment were solid, but the canvas-first flow was something I mostly validated internally and in Figma. One session watching an engineer try to build a complex scene would have surfaced friction faster than another round of my own iteration.

And I'd document the design system earlier. With 35+ modules across a dashboard and a full 3D editor, the patterns I set up front held the redesign together — but I built a lot of it reactively. Formalising it sooner would have saved rework as the feature set expanded.

# From concept to working model. In one pipeline.

**→ Cv Training Pipeline · 2025** · `CV`

![From concept to working model. In one pipeline. thumbnail](/thumbnails/cv-trainer-thumb.png)

A six-stage agent harness on the Claude Agent SDK that takes a CV model from raw images to a verified detector — with a human gate on every irreversible step. Proved it on a gaze-direction model at mAP@50 0.995.

**Metrics:** Computer Vision · MLOps · Claude Agent SDK · 2025

**Live:** https://delbintoehtet-portfolio.vercel.app/work/cv-trainer

*Building a human-in-the-loop CV training harness with the Claude Agent SDK.*

Training a computer vision model means chaining together a stack of disconnected tools — data hosting, labeling, dataset versioning, training compute, evaluation, and deployment — and manually shepherding data through all of them. One wrong move corrupts the dataset. One credit overspend kills a training run mid-way. I built a harness that automates the whole chain while keeping a human in the loop at every step that matters.

| | |
| --- | --- |
| **Role** | AI Developer + Pipeline Architect |
| **Domain** | Computer Vision / MLOps |
| **Stack** | Claude Agent SDK · Roboflow · Ultralytics · Kaggle |
| **Timeline** | 2025 |

- **6** — Pipeline stages
  <br>Intake → Label → Version → Train → Evaluate → Deploy
- **3** — Training backends
  <br>Roboflow cloud, local Apple MPS, and free Kaggle GPU — the user picks at the gate
- **17** — MCP tools
  <br>Everything the agent can reach: project ops, auto-label, export, train, evaluate, predict

**AT A GLANCE · 60 SECONDS**

### One conversation. One working detector.

Training CV models is repetitive, error-prone, and tool-hopping. Data lives in Roboflow. Training runs in the cloud — or on your laptop — or on Kaggle. Evaluation is a CSV file you have to parse yourself. I built a six-stage agent harness on the Claude Agent SDK that automates all of it, pausing for human approval before anything irreversible. The final proof: a gaze-direction detector for paralysis patients, trained end-to-end through the harness, that hit mAP@50 = 0.995.

`Agent Pipeline` · `Human-in-the-Loop` · `COCO Auto-Label` · `Multi-Backend Train` · `MCP Tools` · `Claude SDK`

- **Problem:** Training a CV model chains together data hosting, labeling, versioning, training, and evaluation — all in separate tools, all manual, all easy to break.
- **Method:** A six-stage agent pipeline on the Claude Agent SDK: one lean agent per stage, a human gate on every consequential action, Roboflow as the managed data layer.
- **Decision:** Separate the stages cleanly. Each agent knows only its own tools. Routing, memory, and approvals live outside the agent — in the orchestrator and the gate.
- **Surfaces:** CLI entry point, stage-by-stage prompting, COCO auto-labeler, 3-way training backend picker, append-only run ledger.
- **Outcome:** Runs end-to-end on real data. Gaze-direction eye-tracking model: mAP@50 0.995, precision 0.993, recall 0.990 — trained entirely through the harness.
- **Lesson:** Fine-tuning only earns its keep on custom classes with real labels. If the class is already in COCO, use the off-the-shelf model directly.

**THE PROBLEM**

### 01 · Training a model is a stack of manual steps. All of them breakable.

The tools exist. Roboflow hosts datasets. Ultralytics trains detectors. Kaggle gives free GPU. But none of them talk to each other, and every hand-off is a place where something goes wrong.

You upload images, switch to a labeling tool, come back to generate a dataset version, export it, copy files into a training script, wait for training to finish, parse a CSV for metrics, and then manually decide whether the model is good enough to deploy. Miss one step — wrong augmentation schema, wrong split, wrong model format — and the whole run is wasted.

The other problem: no guardrails. A Roboflow training run burns credits. A bad dataset version gets frozen and used for training. There's no approval step between “I think this is ready” and “I just spent compute on garbage data.”

> The tools work individually. The problem is the hand-offs — and the complete absence of a human checkpoint before anything irreversible happens.

*[image placeholder: The disconnected manual chain — Roboflow → label tool → version → training script → CSV → model]*

**EXPLORE**

### 02 · I mapped the full chain before writing a line of agent code.

Before building anything, I scoped every step a CV practitioner actually goes through: image intake, annotation, versioning, augmentation, training, evaluation, deployment. Each step had a tool. Each tool had a different interface and a different failure mode.

I spent time understanding the Claude Agent SDK — how tool scoping works with disallowed_tools versus tools=, how can_use_tool gates fit into the agent loop, how setting_sources=[] keeps stray config files from bloating every request. I also dug into the Roboflow SDK — and found seven bugs in the process, all of which had to be fixed before the pipeline could work on real data.

> The Roboflow SDK had seven bugs the docs didn't mention. Real-data testing found all of them. You can't build a reliable pipeline on top of untested assumptions about your dependencies.

*[image placeholder: The 7 Roboflow SDK bugs discovered and fixed]*

**DEFINE**

### 03 · What the harness had to guarantee.

After mapping the chain and testing the SDK, the requirements became clear.

- **Human approval on side effects** — Every consequential action — creating a project, uploading images, freezing a dataset version, starting a training run — had to pause for human approval. No silent side effects.
- **Stage isolation** — The label agent shouldn't be able to accidentally trigger a training run. Tool scope had to be enforced at the framework level, not just by prompting the model to behave.
- **It had to work for free** — Roboflow's free tier allows ~2 training runs. The pipeline needed real alternatives: local training on Apple MPS and a Kaggle free GPU backend, so a user with no credits could still complete the loop.
- **Honest auto-labeling** — A COCO-pretrained model can label the ~80 common classes. For anything else, the pipeline hands off to a manual seed loop — and says so clearly rather than silently failing.

*[image placeholder: Pipeline diagram — the six stages with gate markers]*

**ARCHITECTURE**

### 04 · One agent per stage. One gate per consequential action.

The harness splits cleanly into three layers.

Tools (tools/) are the capability layer — what can be done. roboflow_client.py wraps the Roboflow SDK with all seven bugs fixed. trainers.py holds the local and Kaggle training backends. autolabel.py runs COCO auto-labeling and writes Pascal VOC annotation files. cv_tools.py wraps all of it into 17 in-process MCP tools and builds the server the agents mount.

Agents (agents/) are the orchestration layer — how it's driven. stages.py defines one Stage per pipeline step: its allowed tools, its read-only subset, and its system prompt. orchestrator.py builds lean ClaudeAgentOptions per stage — scoping tools with disallowed_tools, disabling built-ins, wiring the gate. gate.py is the human checkpoint: a can_use_tool callback that surfaces four tools for approval (create_project, upload_images, generate_version, train) and auto-approves everything else. ledger.py writes every run to an append-only markdown file.

Reference (reference/) is the knowledge layer — what good looks like. Domain knowledge on augmentation strategy, dataset auditing, and evaluation thresholds is quoted directly into stage prompts.

*[image placeholder: Architecture diagram — tools / agents / reference layers]*

**THE SIX STAGES**

### 05 · The pipeline, told through each step.

With architecture defined and tools verified on real data, the pipeline runs as six sequential agent sessions.

### Stage by stage.

- *Stage 1* — **Intake** Understands the goal, picks the task type (detection / classification / segmentation), and reuses or creates a Roboflow project. Image upload is gated; the agent reports image and class counts before handing off.
- *Stage 2* — **Label** Two paths. For COCO classes, the auto-labeler drafts boxes on 5 sample images for review before committing to the full set. For custom classes, it routes to a seed loop: hand-label a few → quick-train → pre-label the rest. Upload is gated either way.
- *Stage 3* — **Version** Freezes the dataset with deterministic preprocessing (auto-orient + resize) and task-aware augmentation. It refuses to version an empty or unlabeled dataset. generate_version is gated.
- *Stage 4* — **Train** At the train gate the user picks a backend — Roboflow cloud, local Apple MPS, or Kaggle free GPU. Each has its own pre-flight checks and status polling.
- *Stage 5* — **Evaluate — the Stop Gate** Reads metrics (mAP@IoU, precision, recall, per-class), interprets them against an acceptance threshold, and runs the Stop Gate: PASS → deploy, FAIL → pick a fix and route back. The human makes the final call; the agent doesn't rubber-stamp.
- *Stage 6* — **Deploy** Spot-checks the trained model on real images, confirms predictions match the eval verdict, and marks it verified — or routes back if predictions look wrong.

*[image placeholder: Auto-label sample check — five images with boxes, approve / reject prompt]*

### Three training backends, one gate.

- **Roboflow** — Cloud GPU on Roboflow credits (free tier ≈ 2 runs). A pre-flight credit check runs first. Non-blocking start, then poll train_status.
- **Local** — Ultralytics YOLOv8 on Apple MPS or CPU. Completely free. Exports the frozen version, trains in-process, returns best.pt. Blocking until done.
- **Kaggle** — Free cloud GPU. Pushes a private kernel that pulls the Roboflow version, trains with Ultralytics, writes best.pt. Polls kaggle_status, fetches weights with a 3-retry download.

**THE REAL TEST**

### 06 · Eye-tracking for paralysis patients. mAP@50 = 0.995.

The harness was tested on a human-detection dataset first — 921 images, COCO auto-labeled. The pipeline ran end-to-end, but the resulting model was useless: the person class is already in COCO, so fine-tuning a tiny auto-labeled set just distilled and degraded the base model. The lesson was important — auto-labeling a COCO class on a small dataset trains fine, it just can't win.

The second test changed everything. The dataset: a gaze-direction eye-tracking set for wheelchair-assisted paralysis patients — six custom classes (Close, Down, Left, Right, Straight, Up), 210 training / 60 validation / 31 test images, all human-made labels. COCO has no concept of gaze direction. This was exactly the case the harness was built for.

The model passed the Stop Gate and was verified on test images through the deploy stage. A live webcam demo runs on top of the weights — webcam_eye_demo.py runs the gaze detector in real time and prints the control signal (Left / Right / Up / Down / Straight / Close) to stdout.

> The harness didn't just work. It proved the thesis: fine-tuning earns its keep on custom, non-COCO classes with real human-made labels — and for those cases it reaches near-perfect accuracy.

### What this project taught me.

- **Test on real data, not on assumptions.** Seven SDK bugs stayed hidden until real images and real API calls surfaced them. No amount of reading the docs would have found them. The test run was the only reliable audit.
- **Scope tools at the framework level, not in the prompt.** Telling an agent “only use these tools” in a system prompt is advisory. Using disallowed_tools in ClaudeAgentOptions is enforced. One is a suggestion; the other is a constraint.
- **The human gate is the product.** The gate is what makes this a harness rather than a script. Every consequential action pauses for confirmation — and that pause is where the human's domain knowledge enters the loop.
- **Fine-tuning has a clear decision rule.** If the class is in COCO, use the base model. If the class is custom and the labels are real, fine-tune. The eye-tracking result (0.995) versus person-detection (unusable) is the clearest illustration.

**TIME MACHINE**

### If I could go back.

I'd fix the Roboflow SDK bugs earlier — before designing around assumptions about how the API behaved. Finding seven bugs mid-build meant re-routing the pipeline multiple times. A small upfront script exercising every API call on a throwaway project would have surfaced them in an hour.

And I'd build the Kaggle backend last, not third. The P100 / torch CUDA incompatibility, the phone-verification requirement, the transient download breaks — every Kaggle-specific failure mode added surface area before the core pipeline was solid. Local-first, then hosted, then Kaggle as a bonus would have been a cleaner build order.
